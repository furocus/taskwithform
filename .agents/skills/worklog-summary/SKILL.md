# Worklog Summary

次回の本人や別のエージェントが、会話を読み直さず作業を再開できる短い要約を残す。

## 記録先と対象を確認する

- 作業先のAGENTSと、参照される `AGENTS.local.md` を読み、記録するタイミング・範囲・保存先に従う。今回の依頼で明示された保存先を優先する。
- 個人用設定は、例えば `作業ログ: {Vault内のMarkdownファイルへの絶対パス}` の1項目でよい。Vaultの場所やプロジェクト名をskillに固定しない。
- 保存先が不明なら、まずチャットで要約を提示し、保存先を確認する。個人フォルダを広く探索したり、設定ファイル・Vaultを勝手に作ったりしない。
- 保存先が今の実行環境から参照できることを確認する。WSL・Windows・コンテナ間のパスやマウントを推測して書かない。参照できなければ要約を提示し、保存できなかったことと理由を報告する。
- 現在の会話と今回確認した成果を対象にする。別の会話・他人の作業・過去ログを、今回実施したこととして含めない。

## 短く要約する

[作業ログテンプレート](assets/worklog-template.md) の4項目を使い、各項目は原則1〜2文にする。保存先に書式の規約があれば、4項目の意味を保って合わせる。

- **作業**：何のために、何をしたか。調査・計画だけなら、その範囲を明記する。
- **結果・判断**：実際の変更や結論と、再開時に必要な判断理由。提案・未承認・未完了を完了扱いしない。
- **確認**：実行・確認した範囲と結果、必要な未確認事項。テストの存在、実行、成功は区別し、未実施ならそう記す。
- **次**：最初に着手する具体的な作業、または依存する確認事項。残作業がなければ「なし」とする。

関連するファイル・Issue・PR・ADRは、再開に役立つものだけ添える。長い説明や詳細な検証手順は元資料へ参照させる。会話の逐語録、コマンド全履歴、失敗と再試行の羅列、秘密情報や個人データは残さない。確認していない背景や理由は補完しない。

## 保存して確認する

- 指定先が分かり、依頼やAGENTSで記録が指示されていれば、その範囲でMarkdownを保存する。要約の提示だけを求められた場合は保存しない。
- 既存ファイルは、書き込む前に関連箇所・末尾・書式を確認し、既存の内容を保って追記する。現在の会話で自分が作成した同じ作業の節だと特定できる場合だけ、その節を更新して重複を避ける。人のメモや過去ログを書き換えない。
- 指定されたファイルが未作成なら、存在する親フォルダ内に新規作成してよい。親フォルダもない場合や対象が競合する場合は、要約を提示して保存先を確認する。
- 記録日には作業環境で確認したユーザーの現地日付を使う。過去の実施日を記録日から推測しない。プレースホルダーや作成用コメントは完成ログに残さない。
- ログを充実させるためだけにテスト・ビルド・外部通信・環境変更を実行しない。コミットや外部への送信も、記録作業には含めない。
- 保存後に対象箇所を読み返し、内容と追記・更新範囲を確認する。応答は保存先と記録した主題を短く案内し、全文を再掲しない。保存していなければ「保存済み」と言わない。
