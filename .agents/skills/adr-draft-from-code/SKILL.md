# ADR Draft from Code

人が判断理由と妥当性を確認できるADR草案を作る。実装に存在する事実、提案、チームの合意を区別する。

## 対象と規約

- 適用されるAGENTS、個人用指示、既存ADR・索引・テンプレートを読む。担当範囲、保存先、採番、言語、状態表記を既存規約に合わせる。慣例がなければ保存先は`docs/adr/`とする。
- 対象は重要な構成・API契約・データモデル・責務境界などの設計判断。小さな修正や依存パッケージの全一覧を機械的にADR化しない。棚卸しでは担当領域ごとに候補を整理し、1つのADRに1つの判断を記録する。
- 同じ主題の既存ADRを調べ、重複を作らない。既存ADRの更新は依頼範囲だけ行い、未承認の草案で既存の決定を置換済みにしない。
- 対象が不明なら候補と調査範囲を提示する。範囲・保存先に実質的な曖昧さがある場合だけ確認する。

## 記録区分を選ぶ

| 区分         | 記録するもの                                                             |
| ------------ | ------------------------------------------------------------------------ |
| 現状から復元 | 現在の実装・設定、出典で確認できる過去の理由、不明点                     |
| 新規提案     | 解決する課題、提案内容と理由、今回比較する候補、想定される影響と検証計画 |

- 復元では、実装・テスト・資料を読み、必要なら利用できる履歴やIssue・PRも確認する。コードの存在から当時の採用理由・比較候補・決定者・決定日を推測しない。理由が分からなければ「未確認」とし、担当者への質問を残す。
- 新規提案では、現在の実装を基準に、これから変える内容を明示する。今回の比較・提案理由は記録してよいが、過去に検討済みだった事実として書かない。想定効果は実測結果と分け、実装・検証前ならその状態を明記する。
- どちらの区分も初期状態は「草案／未レビュー」。コードが実装済みでも合意済みとは限らない。新規提案を書いただけで実装許可・承認・移行完了を得たと扱わない。

## 根拠と不明点

- 実装・設定・テストは、確認できた現状の根拠として参照する。過去の判断理由は、それを裏づける既存資料・Issue・PR・ユーザーの説明などを出典にする。
- ライブラリの一般的な利点や公式資料は、当時の選定理由の証拠にはならない。今回の提案の判断材料として使う場合は、今回の検討であると明記する。
- 資料と実装が矛盾していたら、双方の出典と食い違いを残す。意図した仕様を断定せず、文書化のためにアプリケーションコードを変更しない。
- コミット日や記録日を決定日に代用しない。未確認の背景を補完せず、重要な不足情報は担当者に確認する質問にする。

## 草案の出力

[テンプレート](assets/adr-template.md)を使い、既存の規約に合わせる。

- タイトルは確認できた選択、または提案であることを具体化する。背景、決定／提案、理由、影響・制約、確認根拠を残し、適用範囲・重要な対象外・未実装部分も記載する。
- 実際の比較、検証、未確認事項、決定日、関連ADRは該当時だけ記載する。復元時の比較履歴と、今回の比較を混同しない。
- 参照にはリポジトリ相対パスと、必要なら見出し・シンボル・テスト名・コミットを添える。個人PCのパスや非共有の添付ファイルに依存させない。
- 採番規則に従い既存ファイルを上書きしない。提示段階で未採番なら「番号未確定」とする。記録日はユーザーの現地日付を確認して使う。
- 本文のファイル名欄、空の任意節、作成用コメント・プレースホルダーを除く。コード・仕様・検証手順の全文は転載せず、判断の要点と参照先に絞る。

## 確認と報告

- テストの存在、今回実行したこと、成功したことを区別する。未実施なら「今回未実施」とする。
- ADRのためだけにテスト・ビルド・Docker・外部通信を無条件に実行しない。必要な確認は依頼範囲と作業先のルールに従う。
- 根拠のない理由・履歴・日付、隠れた矛盾、既存ADRとの重複がないか見直す。新規提案を実装済みと誤記していないかも確認する。
- 作成・更新したADR、確認範囲、未確認事項、検証の実施状況を報告する。人が確認した後にチームの手順で合意状態へ進める。
